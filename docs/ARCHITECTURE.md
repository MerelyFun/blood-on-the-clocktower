# 数据与权限设计

## 运行模式

“仅此浏览器”模式使用 IndexedDB 保存完整魔典，通过 BroadcastChannel 通知同源标签页刷新。每次操作在同一 IndexedDB 写事务中读取旧版本、执行游戏引擎并保存新版本。

开发默认的“本机数据库”模式由 Node HTTP API 和内置 SQLite 提供。浏览器通过 Vite 同源 `/api/local` 代理访问仅监听回环地址的 API。数据库保存在 `.local-data/clocktower.sqlite`（可通过 `LOCAL_DATABASE_PATH` 指定），服务重启不会清空数据。它复用共享游戏引擎，按成员权限返回完整魔典、公开局面或个人视图；房间命令和成员变更使用 SQLite 事务串行处理，操作 ID 用于防止重复提交。剧本和私人笔记同样保存在 SQLite，并按设备用户隔离。

本地身份使用浏览器 `localStorage` 保存的 Bearer 设备凭据，服务端保存凭据哈希。这不是 Supabase 或正式云端账号：不同浏览器、来源（协议、主机或端口）拥有不同身份，清除站点数据后需要重新入座。电脑上的数据库文件由本机操作者控制，适用于受信任局域网测试，不应把开发服务直接作为公网生产部署。

`VITE_BACKEND` 在开发环境默认选择 `local`，显式设为 `supabase` 才连接云端；生产构建默认选择 Supabase。静态托管本身无法提供本机 API。

云端联机模式由 Supabase Auth 确认操作者，Edge Function 负责授权和命令执行，Postgres 事务是事实来源。前端与服务端复用 `supabase/functions/_shared/engine.ts`，但客户端不能绕过服务端授权直接写入完整局面。

以下表名、RLS、Edge Function 与 Realtime 说明针对 Supabase 云端后端；本机 SQLite 采用相应的服务端成员校验和投影，不使用 Supabase 服务。

## 数据分层

| 表 | 内容 | 客户端权限 |
| --- | --- | --- |
| `bt_rooms` | 房间名称、房间码、拥有者和锁定状态 | 活动成员只读 |
| `bt_members` | 用户、角色、申请状态和座位绑定 | 本人可读自己的记录；说书人可读本房间成员 |
| `bt_games` | 完整魔典 JSON 和版本号 | 仅说书人只读 |
| `bt_public` | 公开阶段、座位、生死、事件和复盘 | 活动成员只读 |
| `bt_player_views` | 单个座位的展示身份、私信和回执 | 当前座位绑定者或说书人只读 |
| `bt_signals` | 按公开、说书人或座位划分的刷新信号 | 按当前成员关系过滤 |
| `bt_commands` | 已提交的操作 ID | 普通客户端无权限 |
| `bt_scripts` | 用户保存的剧本 | 所有者读写 |
| `bt_notes` | 玩家私人笔记 | 作者且仍是活动成员时读写 |

完整魔典、公开局面和个人视图是不同投影。真实身份、秘密标记、说书人笔记和其他玩家的私信不会发送给普通玩家后再依赖界面隐藏。

## 命令提交

1. 前端提交命令类型、载荷、房间 ID 和随机操作 ID；说书人命令附带当前局面版本。
2. Edge Function 使用 `auth.getUser` 验证访问令牌，并从数据库读取成员关系。
3. 服务端加载完整局面，检查操作者权限并执行共享游戏引擎。
4. `bt_commit_room` 锁住房间和局面，复核角色、座位、操作 ID、期望版本和座位占用。
5. 同一事务写入完整局面、公开投影、个人投影、操作 ID 和必要的刷新信号。
6. 接口只返回调用者有权读取的投影。

客户端不能写入游戏状态表。写入 RPC 只授予 `service_role`；用于 RLS 成员检查的 SECURITY DEFINER 函数位于不对 Data API 暴露的 `bt_private` schema，并显式设置 `search_path`。

## 同步与重试

Realtime 只传播小型刷新信号，不广播完整魔典或私信内容。收到信号后，客户端重新鉴权读取自己的投影；页面重新可见或网络恢复时也会刷新。

Realtime 正常时，页面可见期间最长约 60 秒补拉一次；连接异常时降为约 10 秒轮询。所有游戏接口响应使用 `no-store`。

请求在客户端超时后可能已经在服务端完成。前端会保留原操作 ID，并允许安全重试；`bt_commands` 用于避免同一操作重复提交。

## 撤权与重绑

成员撤权、座位重绑和游戏提交使用相同的房间锁。新设备绑定成功后，旧用户不能继续读取该座位的新投影或提交操作。已经显示、截屏或离线保存的信息无法从旧设备追回。

## 领域边界

- 剧本角色池、本局角色实例和玩家展示身份分别保存。
- 座位使用稳定 UUID；调整座次只改变顺序，身份、标记、账号绑定和消息继续跟随座位。
- 真实生死与公开生死分开，票权独立于生命状态。
- 提名保留当次门槛和原始选票；公开投影只包含允许公开的汇总结果。
- 处决与死亡是不同事件，特殊票数和强制裁定需要记录原因。
- 导入 JSON 的未知字段保留在 `raw`、metadata 或 extras 中，不作为代码执行，也不直接渲染为 HTML。

## 存档与复盘

日夜切换前自动保存阶段快照，也可手动保存；自动和手动快照共同保留最近 8 个。完整存档包含角色、标记、私信、说书人笔记和事件，仅说书人可以导出。

玩家的 `bt_notes` 不进入完整魔典。恢复操作总是创建新的房间和成员关系，不覆盖原对局。公开复盘只包含说书人明确选择公开的座位信息和说明。

## 按天玩家笔记

`#/notes` 与房间内的私人笔记共用编辑器。笔记本保存参与者、按日主角色与额外状态变化、文字条目以及公开状态快照，不写入 `Game.notes`、魔典导出或公开复盘。`RoleMark` 新增单选 `primary` 与多选 `extra`；旧 `claim` / `guess` 历史保留，在没有新标记时作为展示回退，显式清空会覆盖回退值。旧 `bt_notes` / SQLite `notes` 全文读取为未分日记录，旧行保留，迁移不猜测日期。

桌面显示当天的主角色与额外状态，玩家面板直接按天展示全部信息；公共条目与随手记在统一“笔记”区按天、昼夜分组展示，数据仍保留原 `kind` 与系统来源。新建文字条目默认当天，编辑器可选择旧日期。独立笔记在桌心说书人下方进入下一天，房间笔记自动跟随公开阶段；笔记界面没有顶部日期切换或遮挡功能。

独立笔记及“仅此浏览器”房间的笔记使用浏览器本地存储。联机房间笔记先同步落盘本机草稿，再在输入暂停后写 SQLite `notebooks` 或 Supabase `bt_notebooks`。保存带 `expectedRevision`，冲突保留双方版本；本机 token 检查防止陈旧标签页覆盖。删除等待进行中的保存结束。

SQLite 使用 `{action:'notebooks', operation:'list'|'get'|'save'|'delete'}`；Supabase 使用 `notebook_operation` RPC（参数 `p_operation`、`p_id`、`p_room_id`、`p_data`、`p_expected_revision`）。此笔记 RPC 是上文游戏状态写入规则的例外：登录用户可调用，但函数内部强制本人归属、房间成员权限与版本校验，禁止直接写笔记表。每人每房间只有一本关联笔记，整本上限 1 MB。撤销成员后本人可读已保存笔记，但不能继续写关联房间笔记或读取房间新状态。

公开座位的 `occupantId` 是房间与成员生成的不透明标识，不暴露账号 ID；换座保持标识，换人改变标识。主持人响应增加 `publicRoom`，笔记仅使用这个公开投影而不读取魔典秘密字段。中途开始记录时不推断旧日期的生死和座位。

本设计降低误泄露风险，但不等同于经过独立安全审计；生产部署仍需执行跨账号权限验证。

笔记条目使用交替浅色气泡，日期与昼夜仅显示在分组标题。编辑时插入座位只显示“几号”，内部保留稳定玩家引用。桌面上方的旋转按钮可改变观看方向并保存，座位编号和玩家关联不变。
