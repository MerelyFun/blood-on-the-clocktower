# 数据与权限设计

## 运行模式

本机模式使用 IndexedDB 保存完整魔典，通过 BroadcastChannel 通知同源标签页刷新。每次操作在同一 IndexedDB 写事务中读取旧版本、执行游戏引擎并保存新版本。

联机模式由 Supabase Auth 确认操作者，Edge Function 负责授权和命令执行，Postgres 事务是事实来源。前端与服务端复用 `supabase/functions/_shared/engine.ts`，但客户端不能绕过服务端授权直接写入完整局面。

## 数据分层

| 表 | 内容 | 客户端权限 |
| --- | --- | --- |
| `bt_rooms` | 房间名称、房间码、拥有者和锁定状态 | 活动成员只读 |
| `bt_members` | 用户、角色、申请状态和座位绑定 | 本人可读自己的记录；说书人可读本房间成员 |
| `bt_games` | 完整魔典 JSON 和版本号 | 仅说书人只读 |
| `bt_public` | 公开阶段、座位、生死、事件和复盘 | 活动成员只读 |
| `bt_player_views` | 单个座位的展示身份、私信和回执 | 当前座位绑定者或说书人只读 |
| `bt_signals` | 按公开、说书人或座位划分的刷新信号 | 按当前成员关系过滤 |
| `bt_commands` | 已提交的操作 ID | 普通客户端无权限 |
| `bt_scripts` | 用户保存的剧本 | 所有者读写 |
| `bt_notes` | 玩家私人笔记 | 作者且仍是活动成员时读写 |

完整魔典、公开局面和个人视图是不同投影。真实身份、秘密标记、说书人笔记和其他玩家的私信不会发送给普通玩家后再依赖界面隐藏。

## 命令提交

1. 前端提交命令类型、载荷、房间 ID 和随机操作 ID；说书人命令附带当前局面版本。
2. Edge Function 使用 `auth.getUser` 验证访问令牌，并从数据库读取成员关系。
3. 服务端加载完整局面，检查操作者权限并执行共享游戏引擎。
4. `bt_commit_room` 锁住房间和局面，复核角色、座位、操作 ID、期望版本和座位占用。
5. 同一事务写入完整局面、公开投影、个人投影、操作 ID 和必要的刷新信号。
6. 接口只返回调用者有权读取的投影。

客户端不能写入游戏状态表。写入 RPC 只授予 `service_role`；用于 RLS 成员检查的 SECURITY DEFINER 函数位于不对 Data API 暴露的 `bt_private` schema，并显式设置 `search_path`。

## 同步与重试

Realtime 只传播小型刷新信号，不广播完整魔典或私信内容。收到信号后，客户端重新鉴权读取自己的投影；页面重新可见或网络恢复时也会刷新。

Realtime 正常时，页面可见期间最长约 60 秒补拉一次；连接异常时降为约 10 秒轮询。所有游戏接口响应使用 `no-store`。

请求在客户端超时后可能已经在服务端完成。前端会保留原操作 ID，并允许安全重试；`bt_commands` 用于避免同一操作重复提交。

## 撤权与重绑

成员撤权、座位重绑和游戏提交使用相同的房间锁。新设备绑定成功后，旧用户不能继续读取该座位的新投影或提交操作。已经显示、截屏或离线保存的信息无法从旧设备追回。

## 领域边界

- 剧本角色池、本局角色实例和玩家展示身份分别保存。
- 座位使用稳定 UUID；调整座次只改变顺序，身份、标记、账号绑定和消息继续跟随座位。
- 真实生死与公开生死分开，票权独立于生命状态。
- 提名保留当次门槛和原始选票；公开投影只包含允许公开的汇总结果。
- 处决与死亡是不同事件，特殊票数和强制裁定需要记录原因。
- 导入 JSON 的未知字段保留在 `raw`、metadata 或 extras 中，不作为代码执行，也不直接渲染为 HTML。

## 存档与复盘

日夜切换前自动保存阶段快照，也可手动保存；自动和手动快照共同保留最近 8 个。完整存档包含角色、标记、私信、说书人笔记和事件，仅说书人可以导出。

玩家的 `bt_notes` 不进入完整魔典。恢复操作总是创建新的房间和成员关系，不覆盖原对局。公开复盘只包含说书人明确选择公开的座位信息和说明。

本设计降低误泄露风险，但不等同于经过独立安全审计；生产部署仍需执行跨账号权限验证。
